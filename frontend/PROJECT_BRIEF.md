# 추구미 생산기 (AI Image Producer) — 해커톤 통합 브리프

## 1. 서비스 정의

### 한 줄 소개

사용자의 고유한 인상을 바탕으로 원하는 `추구미(분위기)`를 헤어·메이크업·컬러·패션 등 실행 가능한 변화 전략과 이미지 시뮬레이션으로 바꾸어 주는 AI 퍼스널 이미지 코치.

### 핵심 메시지

> 원하는 얼굴이 아닌, 원하는 분위기를 만들어주는 AI.

사람들은 연예인의 얼굴 자체보다 그 사람이 주는 분위기와 이미지를 원하는 경우가 많다. 이 서비스는 누군가를 복제하거나 외모의 부족한 점을 평가하는 대신, 사용자가 이미 가진 특징을 살리면서 원하는 분위기에 현실적으로 가까워지는 방법을 제시한다.

### 핵심 가치

- 추상적인 `추구미`를 오늘부터 실행할 수 있는 구체적인 행동으로 변환
- 닮은꼴·외모 점수·시술 중심이 아닌 사용자 고유성 및 스타일링 중심
- 현재 인상 → 목표 분위기 → 차이 → 우선순위별 실행 전략의 명확한 흐름
- 비시술 방법을 우선하고 선택 가능한 시뮬레이션으로 변화 모습을 이해시킴

## 2. 타깃 사용자와 문제 정의

### 주요 타깃

- SNS의 `추구미` 문화에 익숙하고 원하는 무드는 있지만 구현 방법을 모르는 사용자
- 자신의 인상을 객관적으로 이해하고 헤어·메이크업·패션 방향을 찾고 싶은 사용자
- 병원 광고나 획일적인 외모 평가보다 개인화된 스타일 조언을 원하는 사용자
- 짧은 시간 안에 시각적 결과와 실행 계획을 받고 싶은 모바일 사용자

### 해결할 문제

1. 사용자는 원하는 분위기를 말할 수 있어도 어떤 요소를 바꿔야 하는지 모른다.
2. 기존 서비스는 닮은 연예인, 외모 점수, 특정 시술 추천에 머무르기 쉽다.
3. `세련됨 53점`처럼 주관적 분위기를 절대 점수로 표현하면 근거와 편향 문제가 생긴다.
4. 얼굴 사진과 생성 이미지는 민감한 데이터이므로 신뢰·동의·삭제 설계가 필요하다.

### 제품 원칙

- 절대 점수보다 `현재 사진에서 강하게 보이는 이미지`와 `강화할 요소`를 서술형으로 제공한다.
- 얼굴 부위 교정이나 성형 추천보다 헤어, 눈썹·메이크업, 컬러·패션, 피부 관리 순으로 제안한다.
- 연예인을 검색하더라도 특정 인물을 복제하지 않고 사용자가 원하는 이미지 요소를 스타일 키워드로 변환한다.
- 병원·시술 연결은 MVP에서 제외하거나 사용자가 명시적으로 선택한 별도 영역으로 분리한다.
- 추천과 광고·제휴를 분리하며, 제휴 여부가 분석 결과에 영향을 주지 않도록 한다.

## 3. MVP 범위

### 반드시 구현할 핵심

1. 시작/온보딩
2. 얼굴 사진 선택 또는 촬영, 미리보기와 재선택
3. 원하는 분위기 키워드 선택(권장: 3개)
4. 분석 로딩 및 실패/재시도
5. 현재 인상 요약
6. 목표 추구미와의 차이 해석
7. 카테고리별 우선순위 변화 전략
8. 추천 전후 분위기 보드 또는 간단한 이미지 시뮬레이션
9. 결과 저장·공유 또는 다시 생성

### 결과 예시

- 목표 추구미: `도시적 · 시크 · 미니멀`
- 현재 강점: 부드러운 인상, 자연스러운 스타일, 밝고 편안한 분위기
- 먼저 강화할 요소: 정돈된 눈썹, 얼굴선을 드러내는 헤어, 저채도 메이크업, 직선적인 액세서리
- 안내: 현재 얼굴의 특징은 유지하면서 스타일링 요소를 통해 목표 분위기를 강화합니다.

### 후순위/확장 기능

- 로그인과 다기기 히스토리
- 고도화된 생성 이미지 및 전후 비교
- 변화 추적, 퍼스널 컬러, 헤어·안경·액세서리·가상 피팅
- 프리미엄 구독, AI Beauty Report, 브랜드 제휴, B2B API
- 병원 상담은 신뢰 원칙과 별도 동의가 준비된 이후 검토

## 4. 유저 플로우

```text
앱 시작/온보딩
→ 사진 촬영 또는 갤러리 선택
→ 사진 확인·재선택
→ 추구미 키워드 3개 선택
→ 분석 요청
→ 로딩
→ 현재 인상 요약
→ 목표 분위기와 Gap 해석
→ 우선순위별 스타일링 전략
→ 분위기 보드/이미지 시뮬레이션
→ 저장·공유·다시 생성
```

### 예외 플로우

- 사진 권한 거부 → 권한 필요 설명 및 설정/재시도
- 얼굴 미검출/여러 얼굴 → 촬영 가이드와 재등록
- 네트워크/API 실패 → 이해하기 쉬운 메시지와 재시도
- 분석 지연 → 진행 상태와 이탈 방지 안내
- 생성 실패 → 기존 분석 결과는 유지하고 생성만 재시도

## 6. 디자인 전달 방식

피그마와 화면 스크린샷을 개발 가능한 명세로 변환한다. 각 화면 문서에는 다음을 포함한다.

- 화면 목적과 진입/이탈 경로
- UI 요소, 문구, 정렬, 스크롤 및 고정 영역
- 버튼·카드·입력의 동작과 활성/비활성 조건
- 기본, 선택, 로딩, 성공, 빈 상태, 오류 상태
- 컬러, 폰트, 간격, 모서리, 그림자, 아이콘 등 디자인 토큰
- iOS/Android 및 작은 화면 대응
- 필요한 API 데이터와 mock 예시
- 디자인 원본에서 확인되지 않은 가정과 확인 필요 항목

## 7. 프론트·백엔드 분업

### 프론트엔드

- 피그마 기반 화면과 공통 컴포넌트 구현
- 내비게이션과 사용자 입력 처리
- 사진 선택/촬영, 미리보기, 권한 처리
- mock 데이터 기반 전체 플로우
- 로딩·성공·실패·재시도 UI
- 백엔드 API 호출, 응답 타입 정의와 결과 표시
- 토큰 저장/전송이 필요할 경우 클라이언트 처리
- iOS·Android 실제 기기 확인

### 백엔드

- 이미지 업로드·검증·삭제 정책
- AI 모델/API 호출과 프롬프트 관리
- 비밀 API 키와 환경변수 관리
- 인증, 사용자·분석 결과 저장(범위에 포함될 경우)
- 요청 제한, 오류 처리, 로깅
- 프론트에 합의된 JSON 응답 제공

### 연결 구조

```text
Expo 앱
→ 얼굴 사진 + 선택한 분위기 전송
→ 팀 백엔드
→ AI 분석/생성 서비스 호출
→ 팀 백엔드가 응답 정규화
→ Expo 결과 화면
```

실제 OpenAI/Gemini 등 비밀키는 모바일 앱, Markdown, GitHub에 넣지 않는다. `.env.example`에는 변수명과 예시 형식만 두고 실제 값은 서버의 Secret/환경변수로 관리한다.

## 8. Expo React Native 프론트 방향

- 기술: Expo React Native + TypeScript
- 라우팅: Expo Router
- 사진: `expo-image-picker` 중심, 촬영이 필요하면 카메라 기능 추가
- 구조: 화면은 `app/`, 재사용 UI는 `components/`, API는 `services/`, 타입은 `types/`, 디자인 토큰은 `theme/` 등으로 분리
- API 준비 전 mock 데이터와 서비스 인터페이스를 사용해 화면을 완성
- 초기 UI/플로우는 Expo Go로 빠르게 확인하고, 네이티브 제약이 생기면 Development Build로 전환
- 연락처 등 불필요한 권한은 요청하지 않고 카메라·사진 권한만 최소 사용
- `EXPO_PUBLIC_` 변수는 사용자에게 노출될 수 있으므로 비밀값 저장 금지

## 9. Codex/AntiGravity 바이브코딩 방식

- 피그마 화면 + 스크린샷 + Markdown 명세를 하나의 작업 계약으로 제공한다.
- 전체 1차 구현 후 Expo에서 확인하고 화면/기능 단위로 반복 수정한다.
- 큰 요청은 디자인 시스템, 공통 컴포넌트, 화면 묶음, API 연결, 검증 단계로 분해한다.
- Codex는 프로젝트 전체 맥락을 유지하며 구현·수정·오류 해결·테스트를 담당하는 메인 도구로 사용하기 좋다.
- AntiGravity는 구조가 고정된 뒤 독립 화면이나 웹 관리자 등 병렬 작업에 보조적으로 사용할 수 있다.
- 두 도구가 같은 파일/기능을 동시에 수정하지 않게 작업 범위를 분리한다.
- 프롬프트에는 `계획만 세우지 말고 실제 파일 구현`, `모든 화면 연결`, `검사 후 오류 수정`, `변경 파일과 미완성 기능 보고`를 명시한다.

## 10. MD 스펙 운영 방식

- `AGENTS.md`: 반드시 지킬 개발·보안·협업 규칙
- `PRODUCT.md`: 제품 가치, 타깃, MVP 포함/제외 범위
- `IA.md`: 화면 계층과 메뉴 구조
- `USER_FLOW.md`: 정상/예외 이동 흐름
- `SCREEN_SPEC.md`: 화면별 UI, 인터랙션, 상태, 데이터
- `DESIGN_SYSTEM.md`: 색상·타입·간격·모서리 등 토큰
- `COMPONENTS.md`: 공통 컴포넌트 변형과 상태
- `API_SPEC.md`: 엔드포인트, 요청/응답, 오류 코드
- `MOCK_RESPONSE.md`: 프론트 선개발용 예시 데이터
- `IMPLEMENTATION.md`: 작업 순서, 완료 조건, 체크리스트

문서는 코드와 함께 갱신한다. 불확실한 항목은 추측으로 고정하지 않고 `가정`, `확인 필요`, `MVP 제외`로 명확히 표시한다.

## 11. 빠른 MVP 목표

프론트·백엔드 2명이 병렬로 바이브코딩하고 기존 이미지 생성 API를 활용한다는 기준의 목표:

- 1~3일: 전체 화면과 내비게이션이 연결된 프론트 시연본
- 3~5일: 사진 업로드와 mock 분석 결과가 동작하는 버전
- 7~10일: 실제 이미지 분석/생성 API까지 연결한 핵심 MVP
- 10~14일: 실제 기기 오류 수정과 발표 가능한 안정화 버전

가장 큰 일정 위험은 얼굴을 유지하며 분위기만 자연스럽게 바꾸는 생성 품질과 모델/프롬프트 반복 테스트다. 발표 경로는 예측 가능하게 만들고 실패 시 사용할 안정적인 데모 데이터도 준비한다.

## 13. 완료 기준

- 신규 팀원이 이 문서만으로 서비스의 목표와 MVP를 설명할 수 있다.
- 사용자가 사진 등록부터 결과 확인까지 막힘없이 완료할 수 있다.
- API가 없어도 mock으로 전체 발표 플로우가 동작한다.
- 프론트·백엔드 계약과 책임 경계가 문서화되어 있다.
- 디자인과 실제 구현의 차이 및 미확정 가정이 기록되어 있다.
- 비밀키가 프론트/문서/저장소에 없고 얼굴 데이터 처리 원칙이 명시되어 있다.
- Expo 실제 기기에서 핵심 플로우가 확인되고 발표용 데모가 재현 가능하다.
