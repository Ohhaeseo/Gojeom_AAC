> 홈화면이랑 루틴 첫 페이지에는 오늘 할 루틴만, 캘린더에 들어가면 하루하루.

## 1. 무엇이 바뀌었나

| | 이전 | 지금 |
| --- | --- | --- |
| 분석 기반 목표 기간 | **없음** (스키마가 NULL 강제) | **AI가 정한다** (4~52주) |

## 2. 🔴 설계에서 갈린 지점

### 주 N회의 요일을 서버가 정하지 않는다

주 3회짜리도 **그 주의 모든 날에 행을 만들고** `weekly_target`에 3을 싣는다.
월·수·금으로 박아 두면 **월요일에 못 한 사람은 그 회차를 영영 잃는다.**
어느 날 할지는 사용자가 그 주 안에서 고른다.

### 주의 경계는 ISO 월요일이 아니라 목표 시작일

수요일에 시작한 목표를 월요일로 끊으면 **첫 주가 5일뿐**이라 그 주만 "주 3회"를
채우기 어려워진다. `startDate.plusWeeks(k)`로 7일씩 끊는다.

### 빈도를 한글에서 파싱하지 않는다

AI에게 `frequencyPerWeek`를 **숫자로** 받는다. `timing`("주 3회 저녁")은 사용자가
읽는 말일 뿐이고, 일정은 숫자로 만든다. 프롬프트가 **둘을 반드시 일치시키라고**
못 박는다 — 어긋나면 "주 3회"로 읽히는데 매일 배정되는 일이 생긴다.

### 행이 늘어나는 것을 받아들였다

V8 주석이 *"매일 반복하면 4주에 168건이 되어 화면이 무너진다"*고 적어 두었지만,
이제 **홈은 그날 것만, 캘린더는 고른 날짜만** 보여주므로 한 화면에 쏟아지지 않는다.
4주 × 태스크 5개 = 140행, 52주면 1,820행이다.

## 3. 🔴 진행률은 행을 세면 안 된다

주 N회는 그 주의 **모든 날**에 행이 있지만 실제로 해야 하는 것은 N번뿐이다.
행으로 세면 4주짜리 주 3회가 **28개 중 12개**로 잡혀 진행률이 100%에 영영 닿지 않는다.

(목표·태스크·주)마다 목표는 N, 완료는 그 주의 완료 수를 **N으로 상한**한 값이다.
넷째 날을 더 체크했다고 120%가 되면 안 된다.

**세는 곳이 세 군데다.** 하나라도 빠뜨리면 화면마다 다른 숫자가 나온다.

| 어디 | 어떻게 |
| --- | --- |
| 목록·서랍 | `RoutineTaskRepository.countProgressByRoutineIds` — 네이티브 SQL (두 단계 집계 + `LEAST`) |
| 상세·완료 체크 | `RoutineService.progressOf` — 이미 태스크를 다 들고 있어 자바로 |
| 화면의 "이번 주 2/3" | `frontend/src/lib/tasks.ts`의 `weeklyProgress` |

같은 태스크인지는 **`title + timing`**으로 가른다 — `TaskTimingSplitter`가 시점마다
나누므로 한 목표 안에서 이 짝은 유일하다. 세 곳이 같은 기준을 쓴다.

## 4. 만들어 보고 찾은 것 넷

**단위 테스트로는 어느 것도 잡히지 않았다.** 실제로 만들어 보고 눌러 본 것이 값을 했다.

### 4-1. 진행률이 상세 화면에서만 틀렸다

저장소 집계는 V15에서 고쳤는데 `RoutineService.detail`과 완료 체크 응답이
**그 질의를 타지 않고** `tasks.size()`로 행을 세고 있었다. 실측에서 `0/112`로 나와서
찾았다(실제로는 48). `progressOf`로 묶었다.

### 4-2. 🔴 사진을 다시 등록하면 500이 났다

`replaceActive`가 기존 프로필을 비활성화하고 새 행을 넣는데, **Hibernate는 액션 큐에서
INSERT를 UPDATE보다 앞세운다.** 그래서 새 행이 먼저 들어가 부분 유니크 인덱스
`ux_profiles_active(user_id WHERE is_active)`에 걸렸다.

> **두 번째 프로필을 만들 때만 터진다.** 첫 등록만 확인하면 영영 지나친다.
> 하필 촬영 품질 게이트가 **"사진 다시 등록하기"를 권하는 동선**을 만들어 둔 참이라,
> 그 버튼을 누른 사용자가 정면으로 맞을 자리였다.

비활성화를 먼저 `flush()`해 고쳤다. 실측 — 같은 계정으로 프로필 2번 등록 → 201, 201.

### 4-3. 🔴 새벽에만 목표 생성이 막혔다 — UTC 날짜

사용자가 01시에 "루틴 만들기"를 눌렀더니 400이 났다. **낮에는 멀쩡하다.**

```
POST /routines → 400
{"code":"VALIDATION_ERROR","details":{"startDate":"오늘 이후 날짜를 선택해주세요."}}
```

`backend.ts`의 시작일 기본값이 `new Date().toISOString().slice(0, 10)`이었다.
**`toISOString()`은 UTC를 준다.** 한국은 UTC+9라 **자정부터 오전 9시 사이에는 어제
날짜**가 나오고, 서버는 `Asia/Seoul` 기준으로 "오늘 이후"를 검사한다
(`RoutineService.requireFutureStartDate`). 그 아홉 시간 동안만 막힌다.

| | |
| --- | --- |
| UTC 기준 오늘 | `2026-08-18` ← 프론트가 보내던 값 |
| KST 기준 오늘 | `2026-08-19` ← 서버가 기준 삼는 값 |

`lib/date.ts`의 `toIsoDate`는 **처음부터 이것 때문에** 로컬 기준으로 만들어져 있었다 —
주석에 *"로컬 날짜 기준이라 `toISOString()`을 쓰지 않는다"*고 적혀 있다.
`backend.ts`가 그것을 쓰지 않고 따로 계산하고 있었을 뿐이다.

> **V15와 무관한, 원래 있던 버그다.** 다만 새벽에 작업하다 처음 드러났다.
> 실측 — 같은 요청에 날짜만 바꿔 `2026-08-18` → 400, `2026-08-19` → 201.

### 4-4. 링이 "5/1176 달성"이 됐다 — 오늘/전체 토글 (`b8179c3`)

V15의 예정된 부작용이다. 일정이 날짜마다 펼쳐지니 전체 합이 네 자리가 됐고,
홈 링이 **오늘 다섯 개를 해낸 사람에게 아직 1,171개 남았다**고 말하게 됐다.

진행률 카드 **안 왼쪽 위**에 **[오늘 | 전체]** 토글을 달았다(사용자가 위치를 이렇게
정했다). **기본은 오늘이다** — 링은 "오늘 몫을 채웠나"를 말하고, 전체 여정은 눌러서
보는 값으로 두었다.

카드가 통째로 루틴 화면으로 가는 Pressable이었어서 **구조를 바꿨다** — 겉은 View,
이동은 몸통(링+미리보기)만 맡는다. 토글을 이동 Pressable 안에 넣으면 누를 때
루틴 화면이 같이 열린다(N-11). 실측으로 토글을 눌러도 경로가 `/home`에 머무는
것까지 확인했다.

실측 — 840개짜리 6개월 목표로: 기본 `0/5` → 전체 `0/840` → 오늘 `0/5` 복귀.

> 브라우저 자동화로 확인할 때 **클릭 직후 같은 JS 실행 안에서 DOM을 읽으면 렌더
> 전 값이 나온다.** 별도 호출로 다시 읽어야 한다 — 한 번 "안 바뀐다"로 오판했다.

## 5. 🔴 V15를 쓰다 물린 것 — N-15를 그대로 반복했다

`ck_routine_source`를 **V1 판 기준으로 다시 써서 V4의 결정을 지웠다.**

V4는 *"분석을 지워도 목표는 남는다"*를 위해 FROM_ANALYSIS에서
`analysis_result_id`의 NOT NULL 요구를 뺐었다. 그것을 모르고 V1 판에 `duration_weeks`
조건만 손봐 다시 썼더니, **근거 분석이 지워진 기존 행 11개**에 걸려 마이그레이션이
실패했다.

```
SQL State : 23514
Message   : "ck_routine_source" 체크 제약 조건을 위반하는 몇몇 자료가 있습니다
```

**제약을 고칠 때는 그 제약을 마지막으로 만진 마이그레이션을 찾아 거기서 출발한다.**
`grep -rn "ck_routine_source" src/main/resources/db/migration/`이면 1초다. (N-15)

이어서 엔티티가 `Integer`인데 DB가 `SMALLINT`라 Hibernate 스키마 검증에서 기동이
막혔다. `Short`로 맞췄다.

## 6. 남은 것

- **홈·루틴 화면의 "오늘 할 일"은 이미 날짜로 고른다**(`todayTasks`). V15로 매일 행이
  생겨 오히려 정확해졌다. 따로 손대지 않았다.
- **캘린더에서 주 N회를 체크하면** 그 주의 다른 날 줄에도 "이번 주 2/3"이 함께 바뀐다 —
  같은 목록에서 세기 때문이다. 화면을 옮겨 다니며 확인하지는 못했다.
- **기존 목표는 옛 일정 그대로다.** V15는 스키마만 바꾸고 이미 저장된 태스크를 다시
  펼치지 않는다. 새로 만든 목표부터 날마다 배정된다.
- 앞 문서에서 넘어온 것 — **안드로이드 Google 로그인**(기기 필요) · 가비아 배포 ·
  `eas.json`의 `CHANGE-ME`.

## 7. 알아두면 시간 아끼는 것

- **제약 조건을 고칠 때는 그것을 마지막으로 만진 마이그레이션부터 읽는다.** (N-15)
  V1을 기준으로 다시 쓰면 그 사이 결정이 조용히 사라진다.

- **`SMALLINT` 컬럼에는 `Short`를 쓴다.** `Integer`로 두면 Hibernate 스키마 검증이
  기동을 막는다 — 컴파일도 테스트도 통과한 뒤 서버를 띄울 때 터진다.

- **진행률처럼 "여러 곳에서 같은 것을 세는" 값은 세는 곳을 먼저 전부 찾는다.**
  이번에 저장소만 고치고 상세를 빠뜨려 화면마다 다른 숫자가 나왔다.

  ```bash
  grep -rn "new Progress(" backend/src/main
  ```

- **첫 번째만 확인하면 지나치는 버그가 있다.** 프로필 재등록, 두 번째 목표, 같은 값
  재저장 — "한 번 더" 해 보는 것이 단위 테스트보다 빠를 때가 있다.

- 🔴 **날짜를 서버로 보낼 때 `toISOString()`을 쓰지 않는다.** UTC라 한국에서는
  자정~오전 9시에 어제가 된다. 이런 버그는 **그 시간대에만 재현되어** 낮에는
  아무리 눌러 봐도 나오지 않는다. `lib/date.ts`의 `toIsoDate`를 쓴다.

  ```bash
  grep -rn "toISOString()" frontend/src   # 날짜를 만드는 자리가 또 있는지
  ```

- **AI를 부르는 경로는 실제로 한 번 태워 본다.** 4~6초·수 원이면 끝나고, 이번 세션의
  버그 셋 중 둘을 그렇게 찾았다. 나머지 하나는 사용자가 눌러 보고 찾았다.

  ```bash
  # 로컬 백엔드 띄우기 (Docker 불필요 · N-17)
  cd backend && set -a && . ./.env && set +a && SPRING_PROFILES_ACTIVE=local ./gradlew bootRun
  ```
